## 1. The goal and the way of working

- **Goal:** make `D:\solver` a professional, **general-purpose** optimisation platform. People describe a problem
  in plain words (or bring data), the Assistant models it, and the platform solves it, verifies it and reports it
  honestly.
- **The method (keep it):**
  1. Test live.
  2. Fix **generally**, never shaped to one problem. The owner insists: "don't forget it is a general purpose
     solver".
  3. Deploy and re-test.
  4. Measure against references.
- **Standing rules from the owner:**
  - The owner signs in to the web app; **never type passwords**. Test credentials for local sample sources are
    fine, but never repeat them in replies.
  - **Tell the owner before restarting the platform.**
  - **Preserve each file's line endings.** Some files are CRLF and some LF: check before writing.
  - Keep fixes general purpose.
- **Machine:** Windows, 20 cores, 32 GB. Docker Compose stack. Timezone Africa/Cairo.

## 2. Stack and layout

  organisation.
- **Solvers:** OR-Tools CP-SAT, GLOP and PDLP; HiGHS; SCIP; IPOPT (casadi); NetworkX; plus metaheuristics and
  the new `layout` solver.
- **Frontend:** React with Vite. Vitest, about 3,400 tests.
- **Assistant:** model `qwen3.5` on vLLM (262k context, thinking off). It is slow: 3–9 min per reply.

- **Main code:**

## 3. How to deploy and test (important: this is how the previous session worked)

**Deploy (the previous session ran in a cloud container and reached the PC through "remote devices"):**
1. Edit and test a copy of the code in a Linux test container (`/root/be`, `/root/fe`, with PostgreSQL;
   `. /root/env.sh`). A new session must rebuild its own test copy, from the repo on the PC or from GitHub.
2. Copy changed files to `D:\solver`. Compare with the PC's file first (ignoring CR), and keep each file's line
   endings.
3. **Rebuild:**
   - The owner keeps `rebuild-watch.bat` running.
   - Create the empty file `D:\solver\rebuild.request`, then poll `rebuild.log` for a line starting `DONE`. A
     rebuild takes about 3 minutes.
   - `rebuild.bat` builds backend, worker and frontend, then runs `docker compose up -d`.
4. **With a migration:** `copy .agent_tmp\migrate.bat rebuild.bat`, request the rebuild, then restore it with
   `copy .agent_tmp\rebuild.bat.orig2 rebuild.bat`. `migrate.bat` builds, runs `alembic upgrade head`, then runs
   `up -d`.
5. **Read-only database or log dumps:** put a temporary `.bat` in `.agent_tmp`, copy it over `rebuild.bat`,
   request a rebuild, then restore `rebuild.bat.orig2`. Examples there: `ps.bat`, `logs200k.bat`, `dumpds.bat`.

**Tests:**
- **Backend:** `python -m pytest -q tests`. The suite takes about 27 min. 13 tests fail only for environmental
  reasons: ClickHouse is absent, there are no repo scripts (`check_isolated`, `digest_compose`), and there is no
  weasyprint (`results_out`).
- **Battery:** `tests/zz_eval_battery.py` covers 21 problem classes against references. All 21 are unchanged.
- **Scale checks:** `tests/zz_eval_scale.py`; `tests/zz_bench_scale.py` (records/links scale benchmark, env
  `BENCH_ITEMS`, `BENCH_CELLS`, `BENCH_PER`).
- **Frontend:** `npx vitest run` and `npx tsc --noEmit`.

**Live tests in the browser** (http://localhost:3010, the owner signs in):

- Send a message to the Assistant by setting the textarea value with the native setter, then a keydown Enter.

## 4. What the last sessions built (all deployed and running)

**Data sources**
- Sources are bound to the records they fill (migration 0114), workspace files are kept by version (0115), and
  refresh can run on a schedule (0116).
- HTTPS web sources: JSON, CSV and Excel.
- **MySQL/MariaDB, SQL Server and Oracle** sources (`databases.py`) follow the same rules as PostgreSQL: approved
  networks, verified TLS, only a SELECT, safe failure classes.
  - MySQL is tested live: product mix from MySQL reached **5,550**, the exact optimum.
  - SQL Server and Oracle are checked without a server only. Their sample servers need the vendors' licence terms
    accepted on the PC, and the owner has not been asked yet.
- **Security fix:** a 422 response no longer echoes a password, token or key.

**Workers and the run clock**
- 3 solve workers with a short-run lane (a quarter of the host kept for runs of 60 s or less).
- No starvation: a long run waiting over 15 minutes blocks smaller long runs from starting first.
- A run's time limit now includes preparation (compile, checks, race); the solve keeps at least half of it.
- Models over 500k nonzeros skip the solver race.
- Compile: a quadratic step made a camp-sized compile take hours; it now takes about 14 s, and symmetry detection
  was fixed the same way.
- **Greedy start** for packing-shaped models (`greedy.py`): a solver never ends below it.

**Honest answers (plan §3)**
- **Facts card:** a card drawn by the platform above each answer that reports a run.
- **Number check:** every number in an answer comes from the results, the person, or one step of arithmetic on
  them; otherwise the answer is sent back once.
- **"Optimal" check:** "optimal" or "best possible" is refused unless proven.
- A solve that settles at once is read through `read_result`.
- In Describe mode, the Assistant may solve any existing scenario the person can read.

**Scale (plan §1)**
- Migration **0117** makes the large tables' tenant checks static SQL, and the insert checks run once per
  statement.
  - Build time for 200k links: 79 s → 26 s. At 1.95 M links: build 212 s, snapshot 23 s, compile 21 s.
- The 200k limits are raised 10× (`app/core/limits.py`).

**Placement without a candidate list (plan §1C/§1D), the newest work**
- **IR rule `place` (version 2):**
  - slots with these decisions: chosen, x and y in cells, turned, aisle side;
  - each slot's size in cells;
  - the free areas as polygons in metres;
  - the grid step and origin;
  - the aisle in cells, with its allowed sides;
  - optional `access` and `access_shape`: entrance features such as doors.
- It has its own model class, `placement`. Only the `layout` solver (`placement.py`) takes it:
  1. greedy passes from a coarse grid down to the exact grid;
  2. ruin and recreate;
  3. small CP-SAT windows using 2-D no-overlap.
  - Bound: free cells / (item cells + half its aisle).
  - Verification is cell by cell, including access.
  - Results: a LAYOUT section in reports, and metre rectangles in the exports.
- `make_layout` gives this form by default, including with `access_layers`. The candidate form is used only when
  asked for.
- **Camp drawing** (`backend/tests/fixtures/camp_layout_layers.dxf`; 1.5 × 0.5 m beds, 0.35 m aisle, any side):
  - candidate form: 0.5 m grid, 1,939 beds in 2 min;
  - placement form: exact 0.05 m grid, **2,386 beds in about 12 s**, against a bound of 2,456;
  - with the 68 doors as access: 2,280 beds after 90 s, still rising.

## 5. What is open (in order of value)

1. **Done 8 October, afternoon: live test of the placement form through the Assistant** (camp drawing, 2-minute
   limit, aisle on any side):
   - without doors: run 146, **2,396 beds** (bound 2,456; earlier 2,386). Greedy start 2,387 in 9 s,
     ruin and recreate +9, CP-SAT windows +0;
   - with the 68 doors: run 147, **2,305 beds** (earlier 2,280). Zone C10 has no door and is left out;
   - both answers verified by the platform; zone counts and the gap in the answers checked against the runs.
   - Fixed and deployed from it (commit after `2086bb8`):
     - run times were stamped with `now()` (the transaction's start), so a 118 s run was stored as finishing
       1.2 s after it started: run times now use `clock_timestamp()`;
     - the HTML/PDF report of a placement run had no map, and a drawing-sized layout was a speck at the zoom
       cap of 18: shapes by metres are now given to the report, and the zoom cap is 22;
     - read-back wording ("along a any side", "a access_point").
   - Then, also deployed:
     - **placement start**: a backward scan now prefers the mirrored aisle side (it packed about 10% worse:
       2,159 against 2,386 beds); every pass, coarse ones included, is scored after access, and the areas are
       combined from whichever pass does best in each (`best_per_zone`, re-checked under the layout's
       rules). Camp with doors, 2 min: **2,347 beds live (run 149), was 2,305**; at 20 s, 2,330 against 2,130.
       Without doors unchanged (about 2,390);
     - the report map draws each record once, its titles naming every decision (2,305 shapes, 849 KB, was
       11,525 and 2.4 MB);
     - read_result says what each export holds, and gives the in-app map link `/runs?scenario=…&run=…`
       (the Assistant had said the GeoJSON showed "the aisles, and the obstacles").
   - **The area bound was not a bound** (fixed and deployed): it counted half an aisle per item, but an aisle
     cell can serve four items (one from each direction), and exact CP-SAT solutions beat it (a 7 x 7 room
     of 2 x 1 items with a 1-cell aisle holds 20; the "bound" said 19, so 19 would have been called proven
     best). Now a quarter of an aisle per item, in `placement.area_bound`, the layout tool's slot count and
     the candidate form's bound; a test checks it against exact optima. The camp's bound is now 2,592
     (2,609 in the candidate form), so its honest gap is larger (2,347 is within about 9.5%). Runs up to 149
     carry the old figure, and models built before have only 2,456 slots, which is then a true bound for
     them. A tighter valid bound needs a relaxation (LP or a band argument): open.
   - Still open: the GeoJSON keeps one layer per decision (each bed 5 times), by design for GIS layers; a
     claim about a file that is not in those words is not caught by the reply checks.
