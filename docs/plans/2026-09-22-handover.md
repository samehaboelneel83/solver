## What was built today

In the order it landed. Every item is committed and deployed.

### Solving

- **Quadratic objectives** (`3bed808`) and **quadratic rules** (`7f7af6f`).
  A goal or a rule may multiply two decisions. The model is then QP/MIQP or
  QCQP/MIQCQP, and only a backend that can prove a global optimum whatever
  the curvature is offered one.
- **SCIP** (`ae67122`) as the global solver, through PySCIPOpt, in the
  worker process (unlike HiGHS it does not clash with OR-Tools). It takes
  the cases that were refused: a continuous model not proven convex, and a
  quadratic goal over mixed decisions.
- **Showcase templates** (`40f0907`): `feed_blend` (LP, fractional answer,
  GLOP) and `load_balance` (convex QP, HiGHS), ensured at start-up.
- **Phase 6 correctness** (`486fef8`, `06fca08`, `007d4c5`, `f94e5ef`):
  - a solver stopped before it found anything no longer returns invented
    values (**D2**, it used to crash on an infinite objective);
  - `unbounded` is a run status, and an answer resting on a ceiling the
    model never set is re-solved with the ceiling raised before it is
    believed (**D5/D9**);
  - the run's seed reaches every backend (**D3**); every answer records the
    solver's best bound and the gap to it (**D6**); a lexicographic stage is
    frozen with a tolerance (**D8**);
  - `solve.gap_rel` and `solve.workers` are settings, and "optimal" now
    requires a closed gap — HiGHS and the pywraplp wrapper used to stop at
    their own 1e-4 default and still say optimal;
  - stopping a run keeps the best answer it had (**D4**);
  - HiGHS builds its model as arrays: 2.0 s → 0.23 s on 200,000 entries,
    and a rule left with no variables is no longer dropped (**D7**, which
    was also a wrong-answer bug).
- **Golden suite** (`backend/tests/test_golden.py`): 15 hand-solved models
  run on every backend that takes them, through the path a run uses.
- **Benchmark harness** (`bafd5ae`, `backend/bench/`): seeded families at
  four sizes, a MIPLIB lane, a runner that marks disagreeing answers wrong,
  and a report with the enable-by-default verdict. First result committed:
  CP-SAT on one thread cannot prove the rota optimum in 20 s; on eight it
  takes 30 ms.

### Tenancy (Phase 7, complete)

- **Every row belongs to an organization** (`68131f1`, migration `0032`),
  filled from its parent by trigger, enforced by row-level security for
  `solver_app` — the role a request switches to, because the app connects as
  a superuser and superusers bypass RLS. **D1 is fixed**: another tenant's
  runs are neither listed, opened nor cancelled.
- **Quotas, metered usage, fair claiming** (`aa45272`, migration `0034`).
- **API keys and a rate limit** (`5f6a00e`, migration `0035`), with a page
  at `/api-keys`.

### The product

- **The Optimization View in four styles** (`4c013ff`): the Cytoscape graph,
  Blockly blocks, a Rete.js node editor and a React Flow chart, all drawing
  the same model with the same node ids, each loaded on first use.
- **Watching a run** (`2588100`, `eb12af8`, `26b9d08`, migration `0036`):
  `run_event` records each better answer and each tightening of the bound
  from the solvers' callbacks, throttled to two a second; `GET /runs/{id}/events`
  streams them; the run page draws the two curves closing.

## What is open

**Phase 8** is complete: progress events, JSON logs, metrics, tracing, run
facts in ClickHouse and `run_event` retention. `run.retention_days` (365,
"how long answers are kept") exists but nothing enforces it.

**Phase 6** is complete (nightly CI, primal integral, D7 everywhere,
CP-SAT scaling measured off, the MIPLIB lane checked against published
optima).

**Phase 7 leftover:** run priority is not modelled; fair claim orders by
organization then age.

**Phase 9** is complete: each solve and diagnosis in a sandboxed child
(`app.solve.sandbox`; `SOLVE_MEMORY_MB`, CPU allowance, deadline).

**Phase 10** has begun: the contract is version 2 (reads 1 and 2) and the
IR is typed as Pydantic models (`app/ir/models.py`).
Conditional rules (`when`) solve natively on CP-SAT and SCIP, and on
HiGHS and the MILP wrapper as a big-M from declared bounds.
Piecewise-linear terms (`pwl`) solve everywhere that can hold them:
CP-SAT as a table, SCIP as SOS2, HiGHS and the MILP wrapper rewritten
(epigraph or incremental), GLOP when an epigraph suffices.
Scheduling (intervals, `no_overlap`, `cumulative`) solves on CP-SAT and
is refused elsewhere with the reason; the editor shows curves and
scheduling read-only until the editor slice. Conditions and curves are
built in the editor (`2ff854d`), which now always publishes version 2;
so are intervals and scheduling rules (`5343dc6`). Phase 10 is complete.

**Phase 11** has begun: a conflict starts from HiGHS's IIS of the linear
relaxation (`79d8b1a`), confirmed and shrunk with the run's own backend;
the run records `conflict_method`, `_probes`, `_seconds`. A CP-SAT run
starts from CP-SAT's own assumption core (`3ec5a42`), exact where only
whole numbers conflict. The run page reads a conflict in the rules' own
notes and says how it was found (`4cd7b4b`). The queue's Phase 11 items
are done; the roadmap's minimum-cost relaxation, diverse IISs and
sensitivity in business language are not in the queue.

**Phase 12** has begun: the result cache (`0a5dd98`, migration 0042) --
a submit whose model, data, patch and deciding settings match a proven
global optimum is recorded already answered, `reused_from` that run;
`reuse: false` solves again. Warm starts (`21bff11`, migration 0043) exist
behind `solve.warm_start`, off: the bench found no win worth the default.

**Phase 13** has begun: symmetry breaking (`bae4704`, migration 0044)
behind `solve.symmetry`, off on the bench's evidence. Frontend test
waits were hardened the same day (`5e9d109`): the lazy expression
builder is loaded before its tests, and no wait is shorter than the
suite's five seconds. Solver options run behind the benchmark gate
(`e69e824`, `app.solve.params`): of eleven measured, SCIP's fast presolve
won and is enabled for every SCIP solve.

**Phase 15** has begun: the trade-off front between two goals
(`1e78f90`, migration 0045), each point a run of its own. A parameter
may declare its uncertainty (`df34fc4`), and a run may ask for a robust
answer (`5827038`): every rule that reads an uncertain value holds for
any Γ of them moving, rewritten exactly (Bertsimas–Sim), with the price
of robustness against the nominal answer on the run page. The frontend
suite now runs on half the cores (`1d5546d`) -- five full-suite-only
flakes in one day, gone at the same wall time. A `workshop` template
shows it (cut then weld, makespan 9), and the bench compares intervals
with time slots (`flow_shop` / `flow_shop_timed`, the latter
comparison-only).

**Phase 16** has begun: a closed function catalogue (`0c89b46`) -- exp,
log, sqrt, abs, sin, cos of a linear argument, each labelled convex,
concave or neither -- written in the editor and solved by SCIP as NLP or
MINLP; an argument whose bounds leave log's or sqrt's domain is refused
by name. DCP detection (`9a1195d`) classifies such a model convex or
names where it is not proven so. An import cycle that failed a fresh
worker's first run of one was fixed at its root (`cde0b7a`), and a test
now imports every module first in a fresh interpreter. Products with a
yes-or-no factor are written exactly as linear rows (McCormick,
`3f71f80`), so such mixed models now solve on HiGHS rather than SCIP.
Quadratic rules are labelled convex, second-order cone, or not proven
convex (`e550d2f`); a model of cones under a convex goal is recorded as a
convex program and needs `socp`.

## Known problems

1. ~~**An intermittent frontend test failure.**~~ **Fixed** (`fb8843c`). The
   race was real and in the product: react-querybuilder reports its query
   once on mount by default, a tick after the render it came from, and in
   the model editor that report climbed value-based handlers and wrote a
   stale copy of the whole rule over an edit made in between (a rule made
   "preferred" snapped back). The builder now reports edits only
   (`enableMountQueryChange={false}`). `vitest --sequence.shuffle` is the
   way to smoke out order dependence: it also found two tests sharing state
   (`useGraphMode`, EntityDetail's PUT count), both fixed. 10 plain and 6
   shuffled full runs green.
2. ~~**`weekly_rota` applied to an empty domain is infeasible.**~~ **Fixed**
   (`e4cd513`, `ca6580e`). It could not be otherwise under a hard coverage
   rule: 21 shifts of capacity against 57 demanded, nine people wanted on
   a weekday out of five. The template's model is now the demo's with the
   `relaxed_cover` softening applied (`weekly_rota_template_ir()`); the
   Workforce demo keeps its hard rule as the infeasibility example. The
   template was also refreshed only by `python -m app.seed`, so start-up
   now refreshes it. Live: a new domain's first run is optimal at 3669,
   the value worked by hand in `test_api_templates.py`.
3. ~~**The app connects to Postgres as a superuser.**~~ **Mostly fixed**
   (`9c2f2be`, migration `0037`). API and worker log in as `solver_runtime`:
   not a superuser, owns nothing, so it cannot change the schema, switch a
   policy or trigger off, create roles or read files (checked live:
   `ALTER TABLE run DISABLE ROW LEVEL SECURITY` is refused). It keeps
   BYPASSRLS, because system code sees every tenant by design. No login
   role could stop injected SQL from leaving its tenant anyway: the tenant
   is the session setting `app.org_id`, and `set_config()` on it is as
   unprivileged as `RESET ROLE` (shown live). RLS guards against app bugs;
   the defence against injection is parameterised SQL, which every query
   here is (checked by grep: interpolated fragments are constants or
   integer route ids). Keep it that way.
4. **Playwright is installed but unlisted.** `frontend/node_modules` holds
   it; `package.json` does not. Any plain `npm install` removes it again
   (`npm install --no-save playwright` puts it back).
5. **Live demo data** still includes the `relaxed_cover` scenario on a
   pre-contract model version, which can never be solved; the Runs page
   explains it rather than offering Solve.
6. **A scheduling model with any fractional data has no solver.** Only
   CP-SAT holds scheduling, and a model whose declared parameters (read or
   not) or constants are fractional needs `fractional-data`, which CP-SAT
   takes only when `solve.cpsat_scaling` is on -- measured off (Phase 6).
   The run errors with "no available solver takes ... fractional-data,
   scheduling". Seen live with the feed template's `cost` (0.3) declared
   but unused. Declaring only the parameters a model reads avoids it; a
   real fix is to count only what the model reads, in `classify._fractional`.
7. **An absent optional interval's start and end are unconstrained,** so
   the roster reports whatever CP-SAT left in them for a job that did not
   happen. (The Remove-guard half of this item was fixed in `5343dc6`.)

## Procedures worth keeping

- **Checks:** `bash scripts/check.sh`. It uses the image `solver-backend`,
  which is the *live* tag — when requirements change, build
  `solver-backend-test` and run
  `SOLVER_BACKEND_IMAGE=solver-backend-test bash scripts/check.sh`.
- **One test file:** `.env` cannot be read from here, so let the container
  derive the URL:
  `docker run --rm --network solver_solver_net -v "D:/solver/backend:/app" -w /app --env-file D:/solver/.env solver-backend-test sh -c 'TEST_DATABASE_URL=${DATABASE_URL}_test pytest -q tests/...'`
- **Migrations against real data:** copy the live database
  (`pg_dump | psql` into `solver_migtest`), run `alembic upgrade head`,
  `downgrade`, `upgrade` again, then drop it. Every migration here has been
  rehearsed that way.
- **Deploy:** build from a clean detached worktree of `HEAD`, migrate with
  `docker compose run --rm --no-deps backend alembic upgrade head` *before*
  restarting, then `docker compose up -d --no-build backend worker
  frontend`. Docker Hub pulls time out now and then; retry.
- **Nightly CI:** `bash scripts/nightly.sh` runs `check.sh` on a clean
  worktree of `master`, then `python -m bench.nightly` (L instances,
  stored in `bench_result`, compared with the night before: wrong answers,
  a moved optimum, a lost proof or a 2x slowdown fail it). Output in the
  gitignored `backend/bench/nightly_results/`; `LATEST` is one line. The
  Windows task `solver-nightly` runs it at 03:00 (`--install`,
  `--uninstall`); Docker Desktop must be running.
- **The runtime login:** `bash scripts/runtime_role.sh` (after migrating
  to `0037`) gives `solver_runtime` a random password and writes its URL
  to the gitignored `.env.runtime`, which compose reads after `.env`; then
  `docker compose up -d --no-build backend worker`. Rerun to rotate the
  password. Delete `.env.runtime` and restart to go back to the owner.
  Migrations (`compose run backend alembic ...`) use
  `MIGRATION_DATABASE_URL`, the owner's URL from `.env`.
- **Logs** are JSON, one object a line (`app.core.logs`); read them with
  `docker compose logs --no-log-prefix worker | jq`, or set
  `LOG_FORMAT=console` for a readable line.
- **Metrics** are on internal ports only: `docker run --rm --network
  solver_solver_net solver-backend python -c "import urllib.request;
  print(urllib.request.urlopen('http://worker:9100/metrics').read().decode())"`
  (the API's is `backend:9101`).
- **Traces:** a run's trace id is in `run.params.trace.traceparent`; its
  spans are `"event": "span"` lines in both containers' logs (or an OTLP
  collector with `OTEL_TRACES_EXPORTER=otlp`). Found so far: `choose` costs
  ~200 ms a run, asking every backend whether it is available.
- **Run facts** are in ClickHouse `run_fact` (read with `FINAL`), written by
  the worker's sweep; tests use the `analytics_test` database. A fact
  outlives its run in Postgres -- it is history -- so a live check that
  deletes its runs should delete their facts too.
- **Solves are sandboxed:** a fake solver monkeypatched in a test is not
  seen by the child -- set `SOLVE_SANDBOX=0` in such a test. To try the
  memory ceiling live: `SOLVE_MEMORY_MB=64 docker compose up -d --no-build
  worker`, then back with plain `up -d`.
- **The nightly job** uses its own test databases (`SOLVER_TEST_SUFFIX=_nightly_test`):
  a check run by hand at 03:00 no longer collides with it. The 2026-09-23
  nightly's `FAIL` for `e0691c0` was that collision, not the code.
- **Live checks:** the scripts used today are throwaway and gitignored
  (`backend/_probe_*.py`, `frontend/_browser_check_*.mjs`). The browser ones
  sign in by writing a signed token into `localStorage`; note that the Runs
  page now holds an event stream open, so Playwright's `networkidle` never
  settles there — wait for `load` instead.
- **A second session may be working in parallel.** Three commits today came
  from elsewhere (`4b69a15`, `3d3853f`, `c38f7ce`), one of them a migration
  that took the number this session had used. Check `git log` before
  numbering a migration, and commit by path rather than `git add -A`.
